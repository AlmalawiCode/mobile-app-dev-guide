المفاهيم التي يجب أن تتعلمها، مرتبة حسب مراحل البناء

هذا أطول فصل في الدليل، وهو مرجع تعود إليه أكثر من كونه قراءة متصلة. لن أعرّف المفاهيم كقائمة قاموس؛ سأرتبها كما ستقابلها فعلًا وأنت تبني تطبيقًا، في خمس محطات: اللغة، ثم الواجهة، ثم البنية والبيانات، ثم حواف المنصة، ثم الجودة والعمر الطويل. في كل مفهوم ستجد ثلاثة أشياء: لماذا تحتاجه، أين يظهر في تطبيق حقيقي، والقرار الذي ستتخذه بشأنه. الأمثلة بلغة Dart، لكن المفاهيم نفسها تنطبق على Kotlin وSwift وTypeScript.

المحطة الأولى: اللغة التي تفكّر بها

المتغيرات والأنواع

لماذا: كل شيء في التطبيق بيانات تتغير: العدد، اسم الذكر، تاريخ الفاتورة. المتغير اسم لصندوق يحمل قيمة، والنوع يحدد ما الذي يجوز وضعه في الصندوق. Dart لغة ذات أنواع ثابتة: إن قلت إن count عدد صحيح، فلن تستطيع وضع نص فيه، ويكتشف المحلل الخطأ قبل التشغيل لا بعده على هاتف المستخدم.

int count = 0;                 // عدد صحيح قابل للتغيير
final String name = 'سُبْحَانَ الله'; // يُحدد مرة واحدة عند التشغيل
const int target = 33;         // ثابت معروف وقت الترجمة
double progress = count / target; // عدد عشري
bool done = count >= target;   // صواب/خطأ
String? note;                  // علامة ? تعني: قد يكون فارغًا (null)

القرار الأهم في Dart: القابلية للفراغ (null safety). علامة الاستفهام تعلن أن القيمة قد تكون غائبة، ويجبرك المحلل على التعامل مع هذا الاحتمال قبل استخدامها. معظم انهيارات تطبيقات المبتدئين في اللغات الأقدم سببها «قيمة فارغة لم يتوقعها أحد». في Dart، الفراغ قرار تعلنه لا حادث تكتشفه. استخدم ? فقط حين يكون الغياب معنى حقيقيًا (ملاحظة اختيارية)، لا كطريقة لتأجيل التفكير.

أين يظهر: نموذج الفاتورة: DateTime purchaseDate إلزامي، لكن int? warrantyMonths اختياري لأن بعض المشتريات بلا ضمان. هذا القرار في النوع يعني أن شاشة التفاصيل يجب أن تعالج حالة «لا ضمان» صراحةً.

الدوال

لماذا: الدالة قطعة منطق لها اسم ومدخلات ومخرج. تفيدك في ثلاثة أشياء: إعادة الاستخدام، وإعطاء اسم واضح لعملية معقدة، والاختبار المنفصل. الدالة الجيدة تفعل شيئًا واحدًا ويمكن اختبارها دون تشغيل الواجهة.

/// هل الضمان ساريًا في تاريخ معيّن؟ دالة نقية: نفس المدخلات تعطي نفس الناتج دائمًا.
bool isUnderWarranty({
  required DateTime purchaseDate,
  required int? warrantyMonths,
  required DateTime today,
}) {
  if (warrantyMonths == null) return false;
  final expiry = DateTime(purchaseDate.year, purchaseDate.month + warrantyMonths, purchaseDate.day);
  return !today.isAfter(expiry);
}

لاحظ أننا مرّرنا today كمدخل بدل استدعاء DateTime.now() داخل الدالة. لماذا؟ لأن الاختبار يحتاج إلى تثبيت «اليوم» ليعطي نتيجة متوقعة. هذا قرار صغير يعلّمك مبدأً كبيرًا: الدالة التي تعتمد على شيء خارجي (الوقت، الشبكة، الملفات) يصعب اختبارها؛ مرّر ذلك الشيء إليها.

الكائنات والأصناف

لماذا: البيانات المترابطة تُجمع في وحدة واحدة. الفاتورة ليست خمسة متغيرات متفرقة، بل «شيء» له اسم وتاريخ وصورة وسلوك (هل ضمانها سارٍ؟). الصنف (class) هو القالب، والكائن (object) نسخة منه.

class Invoice {
  const Invoice({
    required this.id,
    required this.title,
    required this.purchaseDate,
    this.warrantyMonths,
  });

  final String id;
  final String title;
  final DateTime purchaseDate;
  final int? warrantyMonths;

  bool isUnderWarrantyOn(DateTime today) => isUnderWarranty(
        purchaseDate: purchaseDate,
        warrantyMonths: warrantyMonths,
        today: today,
      );

  /// نسخة معدّلة بدل تعديل الأصل: الكائنات غير القابلة للتغيير أسهل تتبعًا.
  Invoice copyWith({String? title, int? warrantyMonths}) => Invoice(
        id: id,
        title: title ?? this.title,
        purchaseDate: purchaseDate,
        warrantyMonths: warrantyMonths ?? this.warrantyMonths,
      );
}

القرار: اجعل نماذج بياناتك غير قابلة للتغيير (immutable) بحقول final ودالة copyWith. حين تتغير الفاتورة، تنشئ نسخة جديدة بدل تعديل القديمة. هذا يمنع فئة كاملة من الأخطاء التي يصعب تتبعها: «من غيّر هذه القيمة ومتى؟».

القوائم والمجموعات

لماذا: شاشة القائمة في كل تطبيق هي في الحقيقة List من الكائنات معروضة عنصرًا عنصرًا. والخريطة Map تربط مفتاحًا بقيمة، وهي ما استخدمناه لحفظ «معرّف الذكر ← العدد». تعلّم العمليات الأربع الأساسية على القوائم لأنها تظهر في كل مكان:

final invoices = <Invoice>[...];
final today = DateTime.now();

final active = invoices.where((i) => i.isUnderWarrantyOn(today)).toList(); // تصفية
final titles = invoices.map((i) => i.title).toList();                        // تحويل
final sorted = [...invoices]..sort((a, b) => b.purchaseDate.compareTo(a.purchaseDate)); // ترتيب (على نسخة)
final byId = {for (final i in invoices) i.id: i};                            // قائمة ← خريطة

البرمجة غير المتزامنة: العمليات التي تستغرق وقتًا

لماذا: قراءة ملف، أو استعلام قاعدة بيانات، أو طلب من الشبكة، كلها تستغرق وقتًا لا يستطيع التطبيق أن «يقف» في انتظاره، وإلا تجمدت الشاشة ولم تستجب للمس. الحل: تبدأ العملية وتعد بأنها ستنتهي لاحقًا، ويواصل التطبيق رسم الشاشة، ثم حين تنتهي تُستدعى بقية الكود. هذا الوعد في Dart اسمه Future، والكلمتان async وawait تجعلانه يُقرأ كأنه كود عادي.

Future<Map<String, int>> loadCounts() async {
  final raw = await prefs.getString('counts'); // انتظر دون تجميد الواجهة
  if (raw == null) return {};
  return decode(raw);
}

// الأخطاء في العمليات غير المتزامنة تُمسك بنفس الطريقة:
Future<void> save() async {
  try {
    await store.saveCounts(counts);
  } on FileSystemException catch (e) {
    log('failed to save: $e'); // لا تبتلع الخطأ بصمت
    rethrow;
  }
}
مصطلح: الخيط الرئيسي (main/UI thread)

الخيط الذي يرسم الشاشة ويستقبل اللمس. في Flutter، كل كود Dart يعمل عليه افتراضيًا، لذلك يجب ألا تُشغّل عليه حسابًا طويلًا (معالجة صورة كبيرة مثلًا)؛ تلك تنقل إلى Isolate منفصل عبر compute(). أما الانتظار (await) فلا يحجز الخيط، لأنه انتظار وليس عملًا.

أين يظهر: في كل مكان يلمس الجهاز أو الشبكة: تحميل العدّ المحفوظ عند بدء التطبيق (لهذا كان لدينا مؤشر تحميل في الفصل التاسع)، حفظ صورة الفاتورة، جلب مواقيت الصلاة. القرار: ماذا يرى المستخدم أثناء الانتظار؟ مؤشر دائري؟ الشاشة القديمة؟ هيكل رمادي؟ وماذا لو فشل؟ صمّم الحالتين معًا.

المحطة الثانية: الواجهة التي يلمسها المستخدم

واجهة المستخدم كشجرة من الـ Widgets

لماذا: في Flutter كل شيء على الشاشة Widget: النص، الزر، الهامش، العمود، الشاشة كاملة. تركّب الواجهة بتعشيش الـ widgets في شجرة، وFlutter يرسمها. الفكرة الجوهرية التي يجب أن تستقر في ذهنك: الواجهة دالة من الحالة. لا تقول «غيّر نص هذا العنصر»، بل تقول «إن كانت الحالة كذا فارسم كذا»، وحين تتغير الحالة يُعاد الرسم.

Column(
  mainAxisAlignment: MainAxisAlignment.center,
  children: [
    Text(dhikr.text, style: theme.textTheme.headlineMedium),
    const SizedBox(height: 24),
    Text('$count', style: theme.textTheme.displayLarge),
    FilledButton(onPressed: onTap, child: const Text('سَبِّح')),
  ],
)

القرار: متى تقسّم الشاشة إلى widgets أصغر؟ القاعدة العملية: حين تتجاوز دالة build شاشة واحدة من المحرر، أو حين تتكرر قطعة في مكانين، أو حين تحتاج قطعة إلى حالة خاصة بها. الـ widget الصغير المسمى جيدًا (CounterDisplay، DhikrTile) يقرأه زميلك ويختبره ويعيد استخدامه.

التنقل بين الشاشات

لماذا: التطبيق ذو الشاشة الواحدة نادر. التنقل يعني إدارة «كومة» من الشاشات: تفتح القائمة فوق شاشة العدّ، وحين تعود تُزال من الكومة. في Flutter الأداة الأساسية هي Navigator:

// افتح شاشة القائمة فوق الحالية
Navigator.push(context, MaterialPageRoute<void>(builder: (_) => const DhikrListScreen()));

// عد إلى الشاشة السابقة (ويمكن إرجاع قيمة)
Navigator.pop(context, selectedDhikr);

القرار: في التطبيقات الصغيرة (2 إلى 5 شاشات) يكفي Navigator المباشر. حين تحتاج إلى روابط عميقة (deep links: رابط يفتح شاشة محددة)، أو تنقّل بشريط سفلي معقد، أو ويب بعناوين URL، انتقل إلى حزمة go_router (من فريق Flutter). لا تبدأ بالأداة الأعقد قبل أن تحتاجها.

إدارة الحالة: أهم مفهوم في تطوير الواجهات

لماذا: «الحالة» هي كل بيانات تتغير مع الزمن وتؤثر في ما يُعرض: العدد الحالي، هل القائمة تحمّل، أي عنصر مختار، هل المستخدم مسجّل دخوله. المشكلة ليست في تخزين هذه القيم بل في إخبار الأجزاء المناسبة من الواجهة حين تتغير، دون تكرار ودون إعادة رسم كل شيء. الفوضى في إدارة الحالة هي السبب الأول في التطبيقات التي «تعمل أحيانًا».

هناك نوعان يجب أن تفرّق بينهما منذ اليوم الأول:

  • حالة محلية للـ widget: هل هذا الحقل مفتوح؟ أي تبويب ظاهر؟ لا يهتم بها أحد غير هذا الـ widget. أداتها: StatefulWidget مع setState.
  • حالة التطبيق: العدد المحفوظ، قائمة الفواتير، المستخدم الحالي. تحتاجها شاشات متعددة ويجب أن تعيش خارج أي widget بعينه. أداتها في هذا الدليل: صنف يرث ChangeNotifier (يحمل الحالة ويعلن تغيّرها) مع ListenableBuilder (يعيد بناء جزء الواجهة المستمع). هذا ما يعلّمه مسار Flutter الرسمي للمبتدئين، ولا يحتاج إلى حزمة خارجية.
class CounterController extends ChangeNotifier {
  int _count = 0;
  int get count => _count;

  void increment() {
    _count++;
    notifyListeners(); // أخبر كل من يستمع: الحالة تغيّرت
  }
}

// في الواجهة:
ListenableBuilder(
  listenable: controller,
  builder: (context, _) => Text('${controller.count}'),
)

تصميم تجربة المستخدم وإمكانية الوصول

لماذا: تجربة المستخدم (UX) ليست الجمال، بل أن يحقق المستخدم هدفه بأقل جهد وأقل أخطاء. وإمكانية الوصول (accessibility) تعني أن يستطيع استخدام تطبيقك من يرى بصعوبة أو لا يرى، ومن يكبّر خط النظام، ومن يستخدم يدًا واحدة. هذه ليست إضافة أخلاقية فقط؛ المتاجر تفحصها (تقرير ما قبل الإطلاق في Play يتضمن فحص إمكانية الوصول)، والمستخدم الذي يكبّر الخط أكثر مما تظن.

قواعد عملية تكفي مشروعك الأول:

  • هدف اللمس: 48×48 dp على الأقل حسب إرشادات Android، و44×44 نقطة حسب إرشادات Apple. زر العدّ في مثالنا يملأ عرض الشاشة عمدًا.
  • التباين: نسبة 4.5:1 على الأقل للنص العادي (معيار WCAG الذي تتبناه المنصتان).
  • لا تعتمد على اللون وحده: عند بلوغ الهدف غيّرنا اللون وأضفنا اهتزازًا؛ أضف نصًا أو أيقونة أيضًا لمن لا يميز الألوان.
  • حجم الخط الديناميكي: اختبر تطبيقك بأكبر حجم خط في إعدادات النظام. النصوص يجب أن تلتف لا أن تُقص أو تخرج من الشاشة.
  • قارئ الشاشة: كل زر أيقوني يحتاج إلى tooltip أو Semantics(label:) حتى يقرأه TalkBack أو VoiceOver. جرّب تطبيقك بعينين مغمضتين مع TalkBack مرة واحدة على الأقل.
  • اتبع لغة المنصة: Material 3 على Android (الافتراضي في Flutter منذ 3.16)، وإرشادات Apple (HIG) على iOS. المستخدم يتوقع أن يكون زر الرجوع حيث اعتاده.

المحطة الثالثة: البنية والبيانات

بنية التطبيق: لماذا نفصل الواجهة عن المنطق عن البيانات؟

لماذا: التطبيق الذي يضع كل شيء في ملف main.dart يعمل في الأسبوع الأول ويصبح مستحيل التعديل في الشهر الثاني. البنية (architecture) هي ببساطة اتفاق على «أي نوع من الكود يعيش أين». الاتفاق الذي توصي به وثائق Flutter الرسمية هو نمط MVVM بثلاث طبقات:

الطبقةما تحتويهلا يجوز أنفي مشروع عدّاد الأذكار
الواجهة (View)Widgets ترسم وتستقبل اللمستحتوي منطق عمل أو تلمس التخزين مباشرةcounter_screen.dart
نموذج العرض (ViewModel)حالة الشاشة والعمليات عليها؛ يعلن التغييريعرف شيئًا عن الـ WidgetsCounterController
البيانات (Repository / Service)القراءة والكتابة من التخزين أو الشبكةتعرف شيئًا عن الشاشاتCounterStore وتنفيذاته

الفائدة العملية الفورية: لأن CounterController لا يعرف الـ widgets، اختبرناه في الفصل التاسع بأربعة اختبارات تعمل في أجزاء من الثانية دون تشغيل واجهة. ولأن CounterStore واجهة مجردة، استبدلناه بنسخة في الذاكرة داخل الاختبار. هذا هو معنى «بنية قابلة للاختبار».

مصطلح: حقن التبعيات (Dependency Injection)

بدل أن يُنشئ الصنف الأشياء التي يحتاجها بنفسه (final store = SharedPrefsCounterStore() داخله)، يستقبلها من الخارج عبر المُنشئ. الاسم مخيف والفكرة بسيطة: «لا تصنع أدواتك، خذها ممن يناديك». الفائدة: يمكن تمرير أداة وهمية في الاختبار وأداة حقيقية في التطبيق.

القرار: لا تنشئ عشرة مجلدات في مشروع من ثلاث شاشات. بنية مشروع صغير:

lib/
  main.dart            // نقطة الدخول: يركّب التبعيات ويشغّل التطبيق
  models/              // أصناف بيانات نقية (Dhikr, Invoice)
  data/                // التخزين والشبكة (CounterStore, InvoiceRepository)
  state/               // المتحكمات / نماذج العرض (ChangeNotifier)
  screens/             // شاشة لكل ملف
  widgets/             // قطع واجهة مشتركة
test/                  // يعكس بنية lib/

المرجع: https://docs.flutter.dev/app-architecture/guide

النماذج والتحقق من المدخلات

لماذا: كل بيانات تأتي من الخارج (حقل نصي، ملف، شبكة) مشبوهة حتى تثبت سلامتها. النموذج (Model) يمثّل البيانات الصحيحة، والتحقق (validation) هو الحارس على بابه. القاعدة: تحقق مبكرًا عند الحدود، وثق بالبيانات في الداخل.

/// نتيجة التحقق: إما نجاح بقيمة أو فشل برسالة قابلة للعرض.
String? validateWarrantyMonths(String input) {
  if (input.trim().isEmpty) return null;          // اختياري: فارغ مقبول
  final n = int.tryParse(input.trim());
  if (n == null) return 'أدخل عددًا صحيحًا';
  if (n < 0 || n > 240) return 'المدة يجب أن تكون بين 0 و240 شهرًا';
  return null;                                     // null = لا خطأ
}

// في Flutter يُستخدم مباشرة مع TextFormField:
TextFormField(
  decoration: const InputDecoration(labelText: 'مدة الضمان بالأشهر'),
  keyboardType: TextInputType.number,
  validator: validateWarrantyMonths,
)

ملاحظات خاصة بالعربية: المستخدم قد يكتب الأرقام بالهندية «١٢» بدل «12»، وقد تُضاف مسافات غير مرئية من لوحة المفاتيح؛ طبّع المدخلات قبل التحقق. والتاريخ يُعرض بالتقويم الميلادي أو الهجري حسب المستخدم، لكنه يُخزَّن دائمًا بصيغة واحدة (ISO 8601 بالتوقيت العالمي).

التخزين المحلي وقواعد البيانات والعلاقات

لماذا: ما لم يُحفظ على القرص يختفي عند إغلاق التطبيق. لكن «الحفظ» طيف واسع، والقرار بين خياراته من أهم القرارات المبكرة:

العلاقات: حين تقول «فاتورة واحدة لها عدة صور»، فهذه علاقة «واحد إلى كثير» تُمثَّل في SQLite بجدول images فيه عمود invoice_id يشير إلى الفاتورة. وحين تقول «فاتورة لها عدة وسوم، والوسم على عدة فواتير»، فهذه «كثير إلى كثير» وتحتاج إلى جدول وسيط. تعلّم هذين النمطين ومعهما 80% من نماذج البيانات في التطبيقات الصغيرة.

قرار غالبًا ما يُهمل: ترحيل المخطط (migration). في الإصدار 2 تضيف عمود «الفئة». المستخدم الذي يحدّث من الإصدار 1 لديه قاعدة بيانات بلا هذا العمود. قاعدة البيانات تحتاج إلى رقم إصدار ودالة ترقية تضيف العمود دون مسح بياناته. تجاهل هذا يعني تقييمات نجمة واحدة بعنوان «التحديث مسح كل فواتيري».

نصيحة شخصية

ابدأ بـ shared_preferences لأي شيء يمكن تمثيله في أقل من بضعة كيلوبايتات (كما فعلنا في العدّاد، وخزّنا الخريطة كنص JSON واحد). انتقل إلى SQLite حين تحتاج إلى بحث أو ترتيب أو علاقات. ولا تلمس NoSQL المحلي في مشروعك الأول.

واجهات البرمجة والتعامل مع الخادم عند الحاجة

لماذا: حين يحتاج تطبيقك إلى بيانات من الخارج (مواقيت صلاة، أسعار، مزامنة)، يتحدث مع خادم عبر واجهة برمجة (API): يرسل طلب HTTP إلى عنوان ويستقبل ردًا غالبًا بصيغة JSON. المفاهيم التي يجب أن تعرفها: طرق الطلب (GET للقراءة، POST للإنشاء)، رموز الحالة (200 نجاح، 404 غير موجود، 401 غير مصرّح، 500 خطأ في الخادم)، وتحويل JSON إلى نموذج Dart.

import 'dart:convert';
import 'package:http/http.dart' as http;

Future<PrayerTimes> fetchPrayerTimes(double lat, double lng) async {
  final uri = Uri.https('api.example.com', '/v1/timings', {'lat': '$lat', 'lng': '$lng'});
  final res = await http.get(uri).timeout(const Duration(seconds: 10));
  if (res.statusCode != 200) {
    throw HttpException('server returned ${res.statusCode}');
  }
  final json = jsonDecode(res.body) as Map<String, dynamic>;
  return PrayerTimes.fromJson(json); // التحقق من الحقول داخل fromJson
}

القرارات: (1) مهلة زمنية دائمًا؛ الشبكة تفشل بصمت. (2) ماذا تعرض حين يفشل الطلب؟ آخر بيانات محفوظة مع تنبيه، لا شاشة خطأ فارغة. (3) لا تضع مفاتيح API سرية داخل التطبيق؛ أي شيء داخل ملف التطبيق يمكن استخراجه. المفتاح السري يعيش على خادمك أنت، والتطبيق يتحدث مع خادمك. (4) استخدم HTTPS فقط؛ المنصتان ترفضان HTTP العادي افتراضيًا.

المصادقة وإدارة الحسابات، إن احتجت إليها

لماذا: الحساب ضروري فقط حين تحتاج بيانات المستخدم إلى الانتقال بين أجهزة أو إلى الارتباط بهوية (دفع، محتوى خاص). تطبيقاتنا الثلاثة لا تحتاج حسابًا في نسخها الأولى. حين تحتاجه، لا تبنِ نظام مصادقة بنفسك أبدًا في مشروعك الأول؛ استخدم خدمة (Firebase Authentication، Supabase، أو تسجيل الدخول بـ Google/Apple).

ما يجب أن تعرفه حتى لو استخدمت خدمة: الفرق بين المصادقة (من أنت؟) والتفويض (ما المسموح لك؟)، وأن الرمز (token) الذي يثبت هويتك يجب أن يُخزَّن في التخزين الآمن للنظام (flutter_secure_storage وأمثالها) لا في shared_preferences، وأن كلا المتجرين يشترط: إن سمحت بإنشاء حساب فيجب أن تسمح بحذفه من داخل التطبيق، وGoogle تطلب إضافةً رابط ويب لطلب الحذف. وApple تشترط تقديم «تسجيل الدخول بـ Apple» إن قدّمت تسجيل الدخول بخدمات طرف ثالث أخرى (راجع البند 4.8 من الإرشادات).
