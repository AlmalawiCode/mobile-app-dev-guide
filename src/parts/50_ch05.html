الأدوات وبيئة العمل: مسار الطالب الذي لا يملك Mac

هذا الفصل يجيب عن السؤال الذي يمنع كثيرًا من الطلاب من البدء: «أملك جهاز Windows أو Linux وهاتف Android. هل أستطيع فعلًا بناء تطبيق يعمل على iPhone؟». الجواب الصادق: نعم لمعظم الرحلة، بشرط أن تفهم بدقة أين تنتهي قدرات جهازك وتبدأ حاجتك إلى خدمة سحابية أو إلى شخص يملك iPhone. نبدأ بتفكيك «تطوير التطبيق» إلى أربعة أنشطة مختلفة، لأن الجواب يختلف لكل نشاط.

القيد الذي لن يزول: محاكي iOS لا يعمل على Windows أو Linux

محاكي iOS (iOS Simulator) جزء من Xcode، وXcode لا يعمل إلا على macOS. لا توجد طريقة رسمية لتشغيله على Windows أو Linux، وأي أداة تدّعي ذلك إما تشغّل macOS افتراضيًا بما يخالف شروط Apple أو تعرض تطبيقك عن بُعد على Mac حقيقي في مكان آخر. حتى وثائق Codemagic تقول صراحةً إنك ستحتاج إلى Mac إن أردت تصحيح تطبيقك تفاعليًا على محاكي أو جهاز iOS. خطّط على هذا الأساس: طوّر واختبر على Android، وابنِ iOS في السحابة، واختبره على iPhone حقيقي عبر TestFlight بمساعدة زميل إن لم تملك واحدًا.

الخطوة 1: تثبيت Flutter SDK

الوثائق الرسمية هي المرجع الوحيد الذي يجب أن تتبعه هنا، لأن الخطوات الدقيقة تتغير: https://docs.flutter.dev/install

الفكرة العامة ثابتة: تنزّل مجلد Flutter وتضعه في مسار لا يحتوي مسافات أو حروفًا خاصة ولا يحتاج إلى صلاحيات مدير (الوثائق تقترح %USERPROFILE%\develop على Windows و~/develop على Linux)، ثم تضيف مجلد flutter/bin إلى متغير PATH حتى يعمل أمر flutter من أي مكان. على Windows تحتاج إلى Git for Windows مثبّتًا مسبقًا؛ على Linux تحتاج إلى حزم أساسية:

# Linux (Debian/Ubuntu): الحزم التي تطلبها وثائق Flutter
sudo apt-get install -y curl git unzip xz-utils zip libglu1-mesa

ثم شغّل الأمر الأهم في حياتك القادمة مع Flutter:

flutter doctor

flutter doctor يفحص بيئتك ويخبرك بما ينقص: Android SDK غير موجود، تراخيص Android غير مقبولة، لا جهاز متصل. اقرأ مخرجاته سطرًا سطرًا ونفّذ ما يقترحه. حين تطلب المساعدة من زميل أو من أداة ذكاء اصطناعي، أرسل مخرجات flutter doctor -v كاملة؛ هي أول ما سيطلبه أي شخص خبير.

حالة الإصدار (تحقق 2026-09-27)

أحدث إصدار مستقر من Flutter هو 3.47.5 (صدر 2026-09-18) ويأتي مع Dart 3.13.4. الإصدارات المستقرة تصدر كل بضعة أشهر؛ ثبّت القناة المستقرة (stable) دائمًا. https://docs.flutter.dev/release/release-notes

الخطوة 2: Android Studio وAndroid SDK والمحاكي

حتى لو نويت الكتابة في VS Code، ثبّت Android Studio لأنه أسهل طريقة للحصول على Android SDK وإدارة تحديثاته والمحاكي. من داخل Android Studio، افتح SDK Manager وتأكد من تثبيت: منصة Android الحديثة (API 36 هو ما تطلبه وثائق Flutter حاليًا)، وBuild-Tools، وCommand-line Tools، وPlatform-Tools، وEmulator. ثم اقبل التراخيص:

flutter doctor --android-licenses
متطلبات النظام (تحقق 2026-09-27)

أحدث Android Studio المستقر هو Quail 4 | 2026.1.4. الحد الأدنى الرسمي: Windows 64-bit (8/10/11) أو Linux 64-bit بـ glibc 2.31 فأحدث، معالج x86_64 من الجيل الثاني من Intel Core أو أحدث أو AMD يدعم الافتراضية، 8 GB ذاكرة، 8 GB مساحة، شاشة 1280×800. للمحاكي توصي Google بـ 16 GB ذاكرة و16 GB مساحة. https://developer.android.com/studio/install https://developer.android.com/studio/run/emulator

المحاكي وتسريع العتاد

المحاكي بدون تسريع عتادي بطيء إلى درجة لا تُحتمل. التسريع يتطلب تفعيل الافتراضية في BIOS/UEFI (تسمى VT-x عند Intel وSVM أو AMD-V عند AMD). على Windows، الوثائق توصي بـ WHPX (منصة Windows Hypervisor، تُفعَّل من «ميزات Windows»)؛ على Linux، تحتاج إلى KVM وأن يكون مستخدمك في مجموعة kvm. المرجع: https://developer.android.com/studio/run/emulator-acceleration

نصيحة شخصية

إن كان جهازك بذاكرة 8 GB فاستخدم هاتفك الحقيقي بدل المحاكي أساسًا؛ أسرع وأصدق. أنشئ محاكيًا واحدًا فقط بشاشة صغيرة (مثل Pixel 8) لاختبار أحجام شاشات مختلفة عند الحاجة.

الخطوة 3: جهاز Android حقيقي

فعّل «خيارات المطوّر» بالنقر سبع مرات على «رقم الإصدار» في إعدادات الهاتف، ثم فعّل USB debugging. وصّل الهاتف بالكابل، واقبل بصمة الحاسوب على شاشة الهاتف، ثم تحقق:

flutter devices

يمكن أيضًا التصحيح عبر Wi-Fi (Wireless debugging) على Android 11 فأحدث. الجهاز الحقيقي يكشف ما لا يكشفه المحاكي: الاهتزاز، سطوع الشاشة، حجم الخط الذي كبّره المستخدم، ضعف الشبكة، والأداء على معالج متواضع. لا تنشر تطبيقًا لم تختبره على جهاز حقيقي واحد على الأقل.

الخطوة 4: المحرر (VS Code أو Android Studio)

كلاهما يعمل جيدًا مع Flutter. VS Code مع إضافة Flutter (تثبّت معها إضافة Dart تلقائيًا) أخف وأسرع بدءًا، وهو ما أرشّحه للطالب. Android Studio أثقل لكنه أقوى في أمور Android الخاصة (تحرير ملفات Gradle، محلل الأداء الأصلي). كلاهما يعطيك: إكمالًا تلقائيًا، وتحذيرات فورية من المحلل، وتصحيحًا خطوة بخطوة، وزر hot reload.

المراجع https://docs.flutter.dev/tools/vs-code https://docs.flutter.dev/tools/android-studio
مصطلح: Hot Reload

ميزة تجعل Flutter يحقن تعديلك في التطبيق الجاري تشغيله خلال أقل من ثانية دون إعادة تشغيل ودون فقدان الحالة. تعدّل لون زر وتحفظ الملف فترى النتيجة فورًا. هذا يغيّر طريقة التعلم كليًا: جرّب، انظر، عدّل.

الخطوة 5: Git وGitHub

Git نظام يحفظ «لقطات» من مشروعك عبر الزمن، بحيث تستطيع العودة إلى أي لقطة، ومقارنة ما تغيّر، والعمل مع زملاء دون أن يكتب أحدكم فوق عمل الآخر. GitHub موقع يستضيف نسخة من مستودعك على الإنترنت. خدمات البناء السحابية تقرأ كودك من GitHub (أو GitLab أو Bitbucket)، فهو ليس رفاهية.

الحد الأدنى الذي تحتاجه من Git في مشروعك الأول، خمسة أوامر:

git init                          # مرة واحدة: ابدأ تتبع المجلد
git add .                         # اختر كل التغييرات للحفظ
git commit -m "add counter screen" # احفظ لقطة بوصف قصير واضح
git log --oneline                 # اعرض تاريخ اللقطات
git push                          # ارفع اللقطات إلى GitHub

مشروع Flutter الجديد يأتي بملف .gitignore جاهز يستثني ملفات البناء. أضف إليه بنفسك أي ملف يحتوي أسرارًا: key.properties، وملف keystore، ومفاتيح الواجهات البرمجية. القاعدة: ما رُفع إلى GitHub ولو لثانية، اعتبره منشورًا.

نصيحة شخصية: متى تحفظ لقطة؟

كلما أنجزت شيئًا صغيرًا يعمل: «زر العد يعمل»، «الحفظ المحلي يعمل». عشر لقطات صغيرة في اليوم أفضل من لقطة كبيرة في الأسبوع، لأن العودة عن خطأ تصبح سهلة ومحددة. وقبل أن تقبل تغييرًا كبيرًا اقترحه الذكاء الاصطناعي، احفظ لقطة أولًا حتى تستطيع التراجع.

الخطوة 6: بناء iOS في السحابة بـ Codemagic

Codemagic خدمة تكامل مستمر (CI/CD) متخصصة في تطبيقات الهاتف، توفر أجهزة Mac في السحابة تبني مشروعك من GitHub وتوقّعه وترفعه إلى TestFlight. ليست الخيار الوحيد (انظر البدائل أدناه)، لكنها الأسهل للمبتدئ مع Flutter لأنها تقدّم Workflow Editor مرئيًا لمشاريع Flutter لا يتطلب كتابة ملفات إعداد.

الأسعار والحدود (تحقق 2026-09-27؛ تتغير كثيرًا)
  • الحساب الشخصي المجاني: 500 دقيقة بناء شهريًا على أجهزة Mac mini M2، بناء واحد متزامن، عدد غير محدود من التطبيقات، ومدة قصوى للبناء 120 دقيقة. الدقائق المجانية لا تتوفر لحسابات الفرق.
  • الدفع حسب الاستخدام: 0.095 دولار للدقيقة على M2، و0.114 على M4، و0.045 على Linux/Windows.
  • تعلن Codemagic عن حسابات مجانية للمعلمين والطلاب والمنظمات غير الربحية.
  • أجهزة البناء تأتي مع Xcode 26.6 افتراضيًا وXcode 27 كخيار حديث، ما يفي بمتطلب Apple الحالي.
https://codemagic.io/pricing/ https://docs.codemagic.io/billing/pricing/ https://docs.codemagic.io/specs-macos/xcode-26-6/

بناء تطبيق Flutter صغير لـ iOS يستغرق عادةً بين 10 و20 دقيقة على هذه الأجهزة، أي أن 500 دقيقة تكفي لنحو 25 إلى 50 بناءً شهريًا. هذا يعني شيئًا مهمًا في طريقة عملك: لا تبنِ iOS مع كل تعديل. طوّر واختبر على Android محليًا، وابنِ iOS عند معالم واضحة فقط.

ما الذي تحتاجه قبل أول بناء iOS؟

  1. حساب Apple Developer مدفوع (99 دولارًا سنويًا). لا توجد طريقة حول هذا للوصول إلى TestFlight أو App Store.
  2. مفتاح App Store Connect API: من App Store Connect ← Users and Access ← Integrations ← App Store Connect API، أنشئ مفتاحًا (توصي وثائق Codemagic بصلاحية App Manager). ستحصل على ثلاثة أشياء: Issuer ID، وKey ID، وملف .p8 يمكن تنزيله مرة واحدة فقط. احفظه في مدير كلمات مرور.
  3. معرّف التطبيق (Bundle ID) مسجّلًا في حساب Apple، وسجل التطبيق منشأً في App Store Connect.
  4. مستودع GitHub يحتوي مشروعك، متصلًا بحساب Codemagic.

بعد ذلك، مع التوقيع التلقائي، تقول وثائق Codemagic حرفيًا إنها «ستنشئ الشهادة وملف التزويد نيابةً عنك دون الحاجة إلى Mac». هذه هي النقطة التي كانت مستحيلة قبل سنوات وأصبحت روتينية اليوم.

المراجع https://docs.codemagic.io/flutter-code-signing/ios-code-signing/ https://docs.codemagic.io/yaml-code-signing/signing-ios/ https://developer.apple.com/help/app-store-connect/get-started/app-store-connect-api

مثال ملف codemagic.yaml مبسّط

حين تتجاوز محرر سير العمل المرئي، تكتب ملفًا باسم codemagic.yaml في جذر المشروع. هذا مثال توضيحي مبني على وثائق Codemagic الرسمية وقت إعداد الدليل؛ راجع صفحة البدء السريع لأحدث صيغة قبل الاستخدام:

workflows:
  ios-testflight:
    name: iOS to TestFlight
    instance_type: mac_mini_m2
    max_build_duration: 60
    integrations:
      app_store_connect: my-asc-key   # اسم المفتاح كما أضفته في إعدادات الفريق
    environment:
      ios_signing:
        distribution_type: app_store
        bundle_identifier: sa.edu.kau.students.dhikr
      flutter: stable
    scripts:
      - name: Get packages
        script: flutter pub get
      - name: Set up signing
        script: |
          keychain initialize
          app-store-connect fetch-signing-files "$BUNDLE_ID" --type IOS_APP_STORE --create
          xcode-project use-profiles
      - name: Build ipa
        script: flutter build ipa --release --export-options-plist=/Users/builder/export_options.plist
    artifacts:
      - build/ios/ipa/*.ipa
    publishing:
      app_store_connect:
        auth: integration
        submit_to_testflight: true

اقرأ الملف كقصة: على جهاز Mac mini M2، بمفتاح App Store Connect المسجّل، جهّز ملفات التوقيع (وأنشئها إن لم توجد)، ثم ابنِ ملف ipa، واحتفظ به، وارفعه إلى TestFlight. المرجع: https://docs.codemagic.io/yaml-quick-start/building-a-flutter-app/

وماذا عن Android في السحابة؟

Android لا يحتاج إلى السحابة لأنك تبنيه محليًا. لكن يمكن أتمتة رفعه إلى Google Play أيضًا عبر حساب خدمة من Google Cloud. تنبيه من وثائق Codemagic: أول نسخة من التطبيق يجب أن تُرفع يدويًا إلى Play Console قبل أن تعمل الأتمتة.

كيف تختبر iOS فعلًا دون Mac؟ خطة واقعية

  1. الاختبارات الآلية على محاكي سحابي: Codemagic يستطيع تشغيل اختبارات التكامل على iOS Simulator داخل أجهزته. تكتب الاختبار مرة وتشغّله على المنصتين في السحابة.
  2. TestFlight على iPhone حقيقي: ابنِ في السحابة، ارفع إلى TestFlight، وادعُ زميلًا يملك iPhone كمختبر داخلي. اطلب منه لقطات شاشة وتسجيل شاشة لكل شاشة في التطبيق، وخصوصًا: الحواف السفلية والعلوية (النتوء والمؤشر)، لوحة المفاتيح العربية، الوضع الداكن، وحجم الخط الكبير.
  3. الاعتماد على تطابق Flutter: لأن Flutter يرسم واجهته بنفسه، فمعظم مشكلات iOS ستكون في «حواف» المنصة: الأذونات، الإشعارات، الملفات، الحفظ في الخلفية. ركّز اختبارك هناك.
  4. جلسة Mac مستعارة عند الحاجة: قبل النشر الأول، ساعة واحدة على Mac زميل أو معمل الجامعة لتشغيل التطبيق على المحاكي ورؤية الأخطاء في وحدة التحكم تساوي أيامًا من التخمين.

قائمة تحقق: بيئتك جاهزة حين…

  • flutter doctor يظهر علامة صح على Flutter وAndroid toolchain والمحرر (تحذير Xcode طبيعي ومتوقع على Windows/Linux).
  • flutter create hello && cd hello && flutter run يشغّل التطبيق الافتراضي على المحاكي أو على هاتفك.
  • تعديل نص في lib/main.dart وحفظه يظهر فورًا بفضل hot reload.
  • لديك مستودع GitHub خاص للمشروع، وأول git push نجح.
  • تعرف مكان ملف .gitignore وما الذي يستثنيه.
  • (لاحقًا، عند الحاجة إلى iOS) حساب Apple Developer نشط، ومفتاح App Store Connect API محفوظ في مكان آمن، وحساب Codemagic متصل بالمستودع.

خلاصة الفصل

  • فكّك «التطوير» إلى كتابة وتشغيل وبناء ونشر. على Windows/Linux تملك الأربعة كاملة لـ Android، وثلاثة منها لـ iOS، والرابع (التشغيل التفاعلي على iOS) يحتاج إلى Mac أو iPhone حقيقي عبر TestFlight.
  • Flutter SDK وAndroid Studio (من أجل SDK والمحاكي) وGit هي الأساس؛ VS Code محرر مريح اختياري.
  • Codemagic يبني iOS ويوقّعه ويرفعه إلى TestFlight دون Mac، بحصة مجانية شهرية تكفي الطالب إن استخدمها بحكمة.
  • الأسرار (keystore، مفاتيح API) لا تدخل Git ولا تُعطى لأداة ذكاء اصطناعي.
